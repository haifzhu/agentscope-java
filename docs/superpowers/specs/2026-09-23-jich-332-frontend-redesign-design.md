## 2. 【核心决策】设计令牌的落地形态

这是整个方案的技术支点。做错，后面 19 个域全部返工。

### 2.1 已验证的事实

我用 Tailwind v4.3.3 实测了候选机制，结论确定：

**Tailwind v4 的 `@theme` 是「引用绑定」，不是「值拷贝」。** 实测编译产物：

```css
@layer utilities {
  .bg-canvas { background-color: var(--color-canvas); }   /* ← 引用变量 */
}
@layer base {
  :root { --color-canvas: #f1f5f9; }
  .dark { --color-canvas: #0a0e15; }                       /* ← 运行时覆盖即生效 */
}
```

因此 **`@theme` 定义令牌 → 在 `:root` / `.dark` 层覆盖同名 CSS 变量 → 全站自动换肤**，且 `bg-canvas` 这类类名可触发 Tailwind 的 tree-shaking（未被令牌化的默认调色板类会被摇掉）。

`dark:` 变体需一行显式声明才能走 class 策略（而非 `prefers-color-scheme`）：

```css
@custom-variant dark (&:where(.dark, .dark *));
```

> 实测产物中 `bg-canvas` 一处定义、无重复，确认变量引用链路成立。

### 2.2 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **① 纯 `@theme` 双主题** | 全部令牌走 `@theme`，`:root`/`.dark` 覆盖 | 改动面最小；56 个文件已用令牌，automatic 生效；支持 tree-shaking | 需要**改掉 `ui/` 组件的默认调色板用法**（约 290 行），否则总闸门不生效 | ✅ **采纳** |
| ② 保留默认调色板 + `dark:` 变体 | 逐处补 `dark:bg-slate-900` | 可渐进 | 783 处 × 2 遍；`dark:` 变体爆炸；与「令牌不可按页面自定义」约束冲突 | ❌ 否决 |
| ③ CSS-in-JS / 引入 styled-components | 换运行时方案 | 主题切换灵活 | 与现有 Tailwind 技术栈冲突；包体积暴涨；上游合并灾难 | ❌ 否决 |

### 2.3 采纳方案的落地形态

**分三层，职责不重叠：**

```css
/* 第 1 层：令牌声明（Tailwind 扫描入口，产生可变类名） */
@theme {
  --color-canvas: #f1f5f9;      /* 浅色默认值 */
  --color-surface: #ffffff;
  --color-text: #0f172a;
  --color-primary: #4f46e5;
  /* ... 色彩/字号/间距/圆角/阴影/动效全量 */
}

/* 第 2 层：运行时主题值（真正的开关） */
@layer base {
  :root { /* 浅色全量令牌 */ }
  .dark { /* 暗色全量令牌 */ }
}

@custom-variant dark (&:where(.dark, .dark *));
```

**令牌命名沿用原型**（`--bg-canvas` / `--text-2` / `--primary` / `--sh-2` 等），因为原型是已评审的设计事实源：

| 原型令牌 | `@theme` 名 | 用途 |
| --- | --- | --- |
| `--bg-canvas` | `--color-canvas` | 页面画布 |
| `--bg-surface` / `-2` / `-3` | `--color-surface` / `-2` / `-3` | 卡片 / 浮层 / 悬浮 |
| `--text` / `-2` / `-3` / `-4` | `--color-text` / `-2` / `-3` / `-4` | 三级文字 + 禁用 |
| `--border` / `--border-strong` | `--color-border` / `-strong` | 边框（装饰） |
| **（新增）** | `--color-border-control` | **表单/可交互控件边框**，需 3:1（§4.2） |
| `--primary` / `--primary-hover` / `--primary-soft` / `--primary-text` | 同名 | 品牌主色四态 |
| `--success` / `--warning` / `--danger` / `--info`（各含 `-soft` / `-text`） | 同名 | 语义色三件套 |
| `--r-sm/md/lg` | `--radius-sm/md/lg` | 圆角 |
| `--sh-1/2/3` | `--shadow-1/2/3` | 阴影（暗色下重定义） |
| `--dur-fast` / `--dur` / `--ease` | 同名 | 动效 |

### 2.4 【修正】为什么必须同时改 `ui/` 组件

实测证据——现有 `Badge` 用默认调色板：

```tsx
// src/components/ui/badge.tsx —— 现状
const tones = {
  success: 'bg-emerald-50 text-emerald-700',   // ← 硬编码，改令牌无效
};
```

若只改 `@theme` 而不动 `ui/`：**组件库纹丝不动，而 56 个用了语义令牌的页面先变了**——结果是组件与页面风格撕裂。

因此 **A1 与 A2 必须作为一个原子改动交付**，且 A2 的第一步是给 `ui/` 组件建立「令牌-only」契约：

```tsx
// 改造后
const tones = {
  success: 'bg-success-soft text-success-text',
};
```

并加 **ESLint 规则禁止在 `src/` 内使用 Tailwind 默认调色板**，把「不可按页面自定义语义色」这条 PRD 约束变成机器可执行的检查——这比写在文档里可靠。

### 3.2 组件契约（每个组件必须满足）

这是防止「组件库不够用 → 页面自己写一套」的唯一手段：

1. **令牌-only**：不出现 Tailwind 默认调色板类、不出现字面色值
2. **双主题**：在 `:root` 与 `.dark` 下均渲染正确，对比度达 WCAG AA
3. **三态齐备**：数据类组件必须同时提供 `loading`（骨架）/ `empty`（现象+下一步）/ `error`（重试）三态，不允许调用方各自实现
4. **可访问**：键盘可达、焦点可见、`aria-*` 完整
5. **有独立示例**：每个组件一个可运行的 showcase 条目（也是 A6 视觉回归的载体）

### 3.3 三态容器（PRD 特别点名）

PRD 5.1.2 指出「空状态/加载中/错误」文案各页面自行编写。收敛为一个受控组件：

```tsx
<AsyncState
  status="error"          // loading | empty | error | ready
  resource="智能体"        // 用于拼装「智能体加载失败」
  onRetry={refetch}
>
  {children}
</AsyncState>
```

文案模板集中在文案层（见 §5），页面只传 `resource` 名。

## 4. 主题机制（A3）

### 4.1 设计

```
优先级：localStorage 用户偏好 > prefers-color-scheme 系统设置
```

| 档位 | 行为 |
| --- | --- |
| `light` | `documentElement.classList.remove('dark')` |
| `dark` | 加 `.dark` |
| `system` | 监听 `matchMedia('(prefers-color-scheme: dark)')` 变化并跟随 |

**防闪烁（FOUC）**：在 `index.html` 的 `<head>` 内联一段阻塞脚本，在 React 挂载前根据 localStorage 设置 `.dark`。这是 PRD 验收 8.3-6「切换 ≤200ms 无闪烁」的必要条件——纯 React 方案必然闪烁。

**过渡**：仅在切换瞬间给 `html` 挂 `.theme-transitioning` 类启用 `transition: background-color/color 200ms`。动效只作用于颜色（PRD 5.1.1 要求「动效仅作用于位移与透明度」——主题色切换是例外，需在方案中显式记录）。

### 4.2 双主题令牌 —— 已推导完成【已定】

原型**只定义了暗色一套令牌**（`--bg-canvas:#0a0e15` 等），无浅色、无切换；而 PRD 验收 5 要求「暗色主题可用」、验收 8.3-6 要求三档切换。线上现状（`index.css` `@theme`）另有一套**浅色**值。

**决策变更**（2026-09-23，片风）：先定「设计师补齐」，后改为 **「授权研发按现有浅色值推导」**。研发已据此完成推导。

**产物**：`docs/superpowers/specs/2026-09-23-jich-332-design-tokens.css`（可直接并入 `index.css`）

推导方法是**语义映射**而非取色：暗色侧每个令牌都有明确语义角色（画布/卡片/浮层、主/次/辅/禁用文字、装饰/控件边框、语义色三件套），浅色侧从现有 `@theme` 取同角色值填入。两套令牌**变量名完全一致**，这是 §2.3 双层结构的前提。

#### WCAG 对比度验证（28 项计算，全通过）

用对比度公式逐项验算，**过程中发现 4 处原型/现有配色不达 AA，已修正**：

| # | 问题 | 原值 | 比值 | 修正 | 修正后 |
| --- | --- | --- | --- | --- | --- |
| 1 | 浅色 `text-3` 在画布上 | `#64748b` | 4.34 < 4.5 | `#526073` | **5.85** |
| 2 | 浅色禁用态 `text-4` | `#94a3b8` | 2.34 < 3.0 | `#7d8ba1` | **3.15** |
| 3 | **原型的 `--border-strong` 当表单边框用** | `#33415a`（暗） | **1.88 < 3.0** | 新增 `border-control` 令牌 | 暗 `#54688f` **3.45** |
| 4 | 白字于实心 success/warning | `#059669` / `#d97706` | 3.77 / 3.19 < 4.5 | `#047857` / `#b45309` | **5.48 / 5.02** |

> **第 3 条是原型的一个真实缺陷**：原型的 `--border-strong` 在暗色下对比度仅 1.88:1，作装饰线可以，但**作表单控件边框不满足 WCAG 1.4.11 的 3:1**。方案新增 `border-control` 令牌专用于可交互控件，`border-strong` 保留作装饰强调线。

**验证口径**：正文/次要/辅助文字 vs 画布与卡片 ≥4.5:1；禁用态 ≥3.0:1（WCAG 豁免非活动控件，此处仍按 3.0 保证可用）；表单控件边框 ≥3.0:1；装饰分隔线 ≥1.2:1（非 WCAG 门槛）；白字于实心语义色 ≥4.5:1。

#### 工具链验证

令牌文件用 Tailwind v4.3.3 **实测编译通过**：
- `.bg-canvas { background-color: var(--color-canvas) }` —— 确认解析为 var 引用（§2.1 的引用绑定成立）
- `.dark { --color-canvas: #0a0e15; ... }` —— 覆盖层完整保留
- `.dark\:bg-canvas:where(.dark, .dark *)` —— `@custom-variant dark` 正确编译为 class 策略

**结论**：A1 的令牌输入已就绪，不再阻塞。

## 5. 其余落地形态

### 5.1 中文化机制（A4）

现状无任何 i18n 框架，全站英文硬编码。

**方案**：不引入 `i18next`（PRD 4.5-11 明确本期只做中文、不做中英切换），采用**轻量文案层**：

```
src/locales/zh-CN/
├── common.ts      # 通用（保存/取消/重试/加载中…）
├── nav.ts         # 导航与路由标题
├── agent.ts       # 智能体域
├── work.ts        # 工作域
├── resource.ts    # 资源域
├── governance.ts  # 治理域
└── index.ts       # 聚合 + 类型
```

```tsx
import { t } from '@/locales';
t('agent.empty.title')        // 「还没有智能体」
```

**为什么不用 i18next**：本期无多语言诉求（YAGNI），引入框架带来包体积与上游合并成本；但**保留按域分文件的结构**，未来接 i18next 只需把 `t()` 换成框架调用，调用点零改动。

**术语表**（PRD 5.1.4 约束）：`Agent`/`MCP`/`Token`/`Webhook`/`Cron`/`API`/`ID`/`URL` 保留英文；首次出现加中文注释，如「智能体（Agent）」。术语映射集中一处，便于审校。

### 5.2 图表能力（A5）

PRD 要求折线/柱状/环形/堆叠条/指标卡/迷你趋势图，单图渲染 ≤500ms，双主题配色**不可反转需分别定义**。

现状已有手写图表代码可作参考：`src/features/operate/components/TokenTrend.tsx`（87 行，柱状趋势）。

**方案对比**：

| 方案 | 体积 | 能力 | 结论 |
| --- | --- | --- | --- |
| **自研 SVG 图表基元** | ~0（复用现状思路） | 覆盖 PRD 全部 6 类；双主题天然可控；无新依赖 | ✅ **推荐** |
| ECharts | ~350KB gzipped | 过剩；主题映射需额外适配；包体积违反 PRD 7.3 首屏 ≤2s | ❌ |
| Recharts | ~120KB | 依赖 d3 子模块；定制受框架限制 | ⚠️ 备选 |

**推荐自研**，理由：PRD 要求的 6 类图表形态固定、数据源明确（Token/成功率/状态分布），自研 SVG 既满足 500ms 预算，又让「图表配色作为设计系统一部分」这条 PRD 约束**天然成立**（同一个令牌文件）。引入 ECharts 会为满足「不可反转」再写一层主题适配，反而更贵。

**注意**：自研需要覆盖 `aria` 与数据表降级（无障碍验收 8.3-7）。这是自研方案的真实成本，不能低估。

### 5.3 信息架构与路由（B1–B3）

### 5.4 【修正】内联样式清理的口径（D1）

### 5.6 【修正】唯一需要动 `api/` 的场景

任务拆分方案的约束 1 说「`api/` 零改动」。实测确认这**基本成立**——但有一个例外必须记录：

若 PRD 的「工作动态」「执行记录」等域需要**新增查询参数**（如按状态筛选的服务端过滤），而现有 `api/` 函数未暴露该参数，则需在 `api/` 加**可选参数**（向后兼容，不改变现有调用语义）。

**约束**：允许新增可选参数；**不允许改变现有函数的入参语义与返回类型**（PRD 8.2 数据验收要求后端零影响）。若某功能必须新增端点，则属范围外，需单列。

| 项 | 做法 |
| --- | --- |
| remote | 本工作区 checkout 源的 `origin` = `haifzhu/agentscope-java` |

## 9. 结论：对任务拆分方案三条建议的回应

| 拆分方案的判断 | 本方案结论 |
| --- | --- |
